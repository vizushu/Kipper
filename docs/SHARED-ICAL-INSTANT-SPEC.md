# Shared iCal instant booking — explicit residual-risk policy

The owner selected custom instant direct booking alongside Airbnb after being told that our importer checks every five minutes and Airbnb imports roughly every three hours. This is acceptance of residual overlapping-booking risk, NOT exclusive inventory, real-time synchronization or a cross-platform lock. The revoked request-to-book implementation is not used.

## Distinct launch contract
`INVENTORY_POLICY=shared_ical` requires `SHARED_ICAL_RISK_ACCEPTED=true`, calendar operations approval, enabled/required inbound sync and enabled export, SQLite support, and explicitly approved operational alert delivery. All existing live booking/provider QA/operations/guest terms and Stripe key/signature checks still apply. Exclusive-direct retains its original independent contract. Unknown policies fail closed. Public preview overrides every booking/payment mode. No flags or credentials are configured by this code change.

## Runtime inventory safety
Retain strict source health and 15-minute local freshness before quotes, atomic local hold creation, payment-intent attachment and atomic confirmation. Each sync lease and successful snapshot is bound to a private fingerprint of the configured feed. Changing the feed invalidates eligibility immediately and retains prior blocks until a successful replacement snapshot; only a match boolean is exposed to authorized status readers. Freshness does not establish freshness of Airbnb's own data. Payment setup must recheck the active hold, imported/manual overlaps and source health immediately before provider setup and again at intent attachment; browser-held secrets cannot guarantee prevention of a late provider charge, so verified late/expired/conflicted payments enter the durable exception ledger rather than confirming.

Importer reconciliation keeps imported ranges even when they collide with a local active hold or confirmed booking. It never overwrites/cancels the guest booking, automatically refunds, silently releases either platform's dates, or treats an import as approval. It records a durable deduplicated incident. Any unresolved incident blocks new holds and confirmations until explicitly reviewed after the actual overlap is resolved. Repeated imports do not flood notifications. Reopened incidents require a new alert episode, not reuse of an already delivered alert.

## Durable operator alerts
Persist safe operator alert jobs in the same SQLite transaction as calendar incident/payment-exception creation. Include only opaque incident/reference identifiers and generic action-needed text, not raw feed URLs, tokens, event descriptions, guest names or payment credentials. Host authentication is required to inspect detail. Bounded leases/retries and stable provider idempotency keys prevent uncontrolled duplication; resolved/acknowledged incidents do not imply a refund. Preview never sends or claims jobs. Real delivery remains separately gated by verified provider, sender and monitored operator recipient; alerting must not depend on source health being good or the live-payment gate remaining open, because failure is when alerts matter.

The current sync-only cron must remain sync-only; this increment does not expand its credential or activate email delivery. Alerts can be persisted while delivery is off. A verified recurring alert dispatcher and provider test remain launch prerequisites.

## Acceptance
Synthetic tests cover shared-vs-exclusive gate independence, preview override, missing risk acceptance/calendar/alert gates, stale/future/failed/conflicted sources, source changes before intent attachment/confirmation, overlapping local transactions, duplicate/reopened calendar incidents, paid-but-conflicted events, durable alert retries/deduplication and no private payload leakage. Preserve current 3BR/max8 and March1 expansion gates, immutable accepted terms, existing payment evidence validation and guest access privacy. Real Stripe/email delivery, cross-platform timing/incident rehearsal, final owner release approval and a maintained response procedure remain outside code-only readiness.

## Operational activation checklist (not performed by this increment)
- Configure a valid server-only Airbnb source and strong private export capability; initial successful snapshot and freshness remain checked inside local inventory transactions.
- Shared policy additionally requires `OPERATOR_ALERTS_APPROVED`, `OPERATOR_ALERT_DELIVERY_QA_APPROVED`, verified live email sender/monitored recipient and a DISTINCT high-entropy `OPERATOR_ALERT_WORKER_SECRET`.
- A separately authorized dispatcher calls POST `/api/operator-alerts/run` with Bearer authorization. The existing calendar cron is NOT repurposed and receives no extra credential. Public preview blocks this dispatcher regardless of approvals.
- Dispatcher examines stale/failed/missing calendar state and queues generic health alerts. It must run even when bookings are closed. Successful real delivery processing updates a private heartbeat; shared-live inventory checks require a heartbeat younger than15minutes with no dead/overdue alert jobs. Synthetic delivery never certifies readiness.
- Admin GET `/api/admin/operator-alerts` reports safe delivery state and heartbeat. An exhausted retry budget requires explicit operational remediation, not automatic key/budget reset. Acknowledging an incident is not a cancellation or refund.
- If a provider intent is created but inventory changes before attachment, no client secret is returned. A durable private setup-reconciliation record is retained; any later paid event still enters existing verified payment exception handling.

If persistence itself is unavailable after provider intent creation, the route returns a generic failure without credentials; it cannot promise a durable record was written during that outage. Subsequent verified provider events remain independently reconciled. Operator/provider reconciliation after storage outages is still required.
